# CGS Wiki workspace and reference coverage

This design describes the complete Wiki target, the current gaps, and the proposed delivery order. The current app is a partial W1 implementation at `a223384`. The owner confirmed that article revision history, comparison, and restore follow the complete Wiki release. In-world history remains a release requirement. The [acceptance checklist](CGS_Wiki_Acceptance_Checklist.md) gives independently testable requirements and their delivery passes.

## Design authority

1. **CGS sources and owner decisions.** Lucidchart **Wiki.pdf** defines the entity and field inventory, measures, relationships, history, actions, assets, and editorial graph. **CGS 2.0 Brainstorm.pdf** adds character structure, institutions, cognition, behavior and state. **CGS.pdf** and the workflow overview describe how world records feed fiction, documentary, and other media. The latest world-model decision distinguishes authoring, dated world history, simulation runs, and editorial order.
2. **World Anvil.** Use its authoring workflows as the reference for building worlds through templates, maps, timelines, calendars, linked relationships, and planning.
3. **Fandom.** Use its encyclopedia workflows for reading, navigating, linking, reusing, and formatting Wiki content. Add its distinct contributions to the same CGS workspace.

Compare features by the task they perform and the records they use. When two features cover one task, build one CGS workflow and take the most useful compatible details from each. For example, one Map record supports World Anvil-style layers and linked articles, Fandom-style marker filters and embedded maps, and CGS's dated places, events, and source links. A feature enters the release checklist with a source, an intended workflow, and evidence of completion. The UI, icons, layout, and sample world use an original CGS design. [World Anvil interface](https://www.worldanvil.com/learn/interface/interface-guide) · [World Anvil public world example](https://www.worldanvil.com/w/cathedris-stormbril) · [Fandom navigation](https://community.fandom.com/wiki/Help%3ANavigation)

## Source trace and design decisions

Start with a source audit inside **W1 workspace**, and complete the relevant detail inside every subsequent pass. The [CGS field trace](CGS_Wiki_Field_Trace.md) is the source inventory for named entity and class types, properties, connections and consumers. The [acceptance checklist](CGS_Wiki_Acceptance_Checklist.md) adds named reference workflows and release checks. Record source page or conversation decision, direct reference guide section where applicable, and the applicable check for each element. Group related elements for reading only when the underlying records and evidence can be checked individually.

For an affected workflow, specify the browser entry point, its eligible logical types and controls, the authoritative Django read or write operation, and PostgreSQL ownership or derivation. A type definition needs field data types, required and optional values, units and constraints. A connection needs named source and target types, direction, cardinality, ownership, time, visibility and valid inverse behavior as applicable. Show where the data feeds timeline, knowledge, rules, simulation or media. Verify the affected nodes and edges in the [editable architecture](CGS_Codex_Local_Handoff/CGS_First_Playable_Architecture.drawio). A logical type may share a storage model when its fields, behavior and identity remain explicit.

For each addition, removal, rename, changed default, merged or split type or field, moved connection, or different reference workflow, record what the source intended, the concrete change, the reason and trade-off, the immediate benefit, and the impact on general-purpose world modeling and later consumers. Cite the affected field or check and the evidence that its intended behavior still works, or state the accepted gap. If a change lacks a defensible reason, carry the source concept forward. Record conflicting sources and the priority used to resolve them.

An unchanged design delivered in a later pass has a named milestone, prerequisite and acceptance check. A temporary substitute also needs a replacement or compatibility plan, including how saved records and IDs move forward, what will trigger that work and how to verify it. Mark the target and the substitute separately so progress reports can identify which version is in the browser.

## Workspace design

| Destination | Author and reader paths |
| --- | --- |
| **World overview and All articles** | A curated world home with an editable introduction and links. All articles has type, category and tag filters, sort, and a useful empty state. Search spans the whole authorized world and can find names, aliases, text, and relevant record types. |
| **People & species, Places, Organizations, Items, Vehicles** | Visible destinations with context-specific creation actions and applicable filters. Each destination accepts a deep link. A vehicle can also appear in a wider item collection through its classification and retain one ID. Subtypes such as building, settlement, nation, and species have named directories. |
| **Maps** | Browse maps, create from an image or a measured layout, select layers and features, follow links, and view a linked event on a map. A Map article can be opened from a place or embedded in an overview. |
| **Timeline & calendars** | Author hierarchical events, action details, eras, and calendars. Choose outline, chronology, or map-linked history. Date and viewpoint controls appear with the question they answer. An article can open its own history without a world-wide date control in the header. |
| **Relationships** | Open family trees, organization and content hierarchies, and relationship or diplomacy diagrams. Select a link to inspect its effective dates, type and source. Use the same link from either endpoint. |
| **Rules & systems** | Browse and edit world laws, role and permission structures, technology, actions and powers, quantities and units, and reusable definitions. A rule preview shows the input, scope, result, and findings. |
| **Planning** | Keep ideas, notes, world premise and themes, boards, plots and subplots, outlines, scenes and manuscript sections, campaign preparation and session reports. Link records and see whether a note is proposed, historical, or an editorial selection. |
| **Sources & media** | Organize images, textures, models, audio and other assets, archival sources, and in-world documents. A citation or asset can be reused across articles and works. Inspect attribution, original source, context, and access. |

The main article is a readable page with a title, introduction, overview panel, section contents, structured facts, related records, history, sources, and media where applicable. Build mode opens the matching template, fields, and relationship controls. Read mode presents the same approved records and article content. A restricted viewpoint is a preview of authorized information. Real account rights still govern which world and underlying records the caller may access.

**Creation paths.** From Vehicles use **New vehicle** to select a template, choose or create linked records, and save a readable article. In the workspace pass Maps offers **Add map reference** for the existing locator workflow and gives measured layouts a distinct label. **New map** opens the image upload and pin editor once the map starter ships. The later spatial pass adds layers and regions. Global **New** offers the same available creation forms, and the manual planning pass adds quick capture. Context sets the type and relevant links. Temporary position belongs in dated state, an event effect, or a later simulation run setup. A map's scale, reference system, and local floor plan settings belong with the map or layout.

**Time and visibility.** The normal workspace header carries the world, global search, reading and building mode, and creation. Normal article reading shows the authored overview, identity and references that have a defined time-independent meaning. Date-dependent values belong in History with their effective date or interval. A default article route has no implied date. In particular, an existing record at tick zero retains its historical meaning. Timeline filters choose time spans. A map can open a historical layer. A dated edit asks when a change becomes true, and an author correction identifies the existing fact or interval being corrected. Calendar settings live in Timeline & calendars. Honor existing `at`, `entry`, `event`, and `view_as` deep links and carry their applicable context into the selected article, timeline, or historical view. Keep the legacy exact-date API contract available during the UI transition.

An identity may appear in several catalog destinations. A ferry has one identity with a vehicle classification and may also appear in Items. Its deck can be a linked Place with its own layout. Catalog membership can come from an explicit instance template or classification. Moving, reclassifying, or retiring the ferry in world history is a dated assertion or a recorded event effect. For an existing item with an unambiguous authored Vehicle classification, expose a Vehicles link to its existing ID while preserving the source fact and effective date. Show uncertain or competing legacy classifications in the Items catalog with their dated evidence for review. A character's biography can link their birthplace and family. Current and former whereabouts come from dated facts or event effects, and their article history opens the same event tree that the Timeline displays. An event venue or someone else's observation conveys its own meaning.

## Full-stack design

- **React workspace.** Add a route per catalog or tool, and one stable article route that can open from search, map, timeline, related links, or a saved bookmark. Shared catalog metadata drives labels, sort and filters, applicable templates, and scoped field or relation editors. Add tabs for prose, facts, history, and sources. Migrate old Library links to the equivalent destination and record. Keep existing IDs and compatibility reads when introducing new paths.
- **Django and PostgreSQL.** Keep the existing world, scoped entry identity, assertions, relationships, events, observations and change receipts. An entity identifies a subject. An article presents that subject or provides standalone editorial content. A source identifies evidence and can link to a document, recording, artifact or person. A work selects and arranges records for a particular output. Store checked article blocks, source citations, and work selections as links to stable IDs. Add reusable template, section, category, and tag definitions. Add Map, Layer, Feature, Calendar, Source, Asset, and Planning records where their lifecycles differ. Prefer an attached article over copying structured values into prose. The same linked records serve the Wiki, other media, and future runs.
- **Write contract.** Extend the scoped, atomic Wiki command service for each workflow. Apply authorization, type and scope checks, conflict handling, and change receipts to the full edit. Prose edits, canonical corrections, dated changes, and proposed changes have explicit meanings. Bulk import validates a preview and applies the approved group once. Stable IDs and the existing edit counter support future editorial revisions. Asset storage validates an upload before linking it, and a failed edit leaves no published metadata or usable link to that upload.
- **Read contract.** Use a shared server projection for catalog, article, timeline, map, relations, search and media. Account rights first limit world access. Audience and fictional character knowledge further limit the intended view. Apply the projection before returning search snippets, labels, counts, embedded records, or derived views. Use indexed names and aliases first, then PostgreSQL full-text search over approved content. Return provenance and stable IDs where visible. An editor selects records into a work and independently chooses presentation order. A simulation initializes from authorized Wiki records and owns its run state and outcomes. During the workspace pass, whole-world name search is an authorized Build workflow. Broader audience and actor search uses the shared projection after W1 visibility checks.
- **Map contract.** The W1 image editor stores marker coordinates relative to the image and links each editable marker to a same-world Place. Pan and zoom change the view, and keyboard users can select and edit markers through a list. A measured layout uses its own units, geometry and connection endpoints. Geographic layers need an explicit reference and scale for physical measurements. Reuse compatible Map IDs and preserve legacy asset references until an author attaches or verifies a replacement. Media reads use the same audience restrictions as linked content.
- **Storage and development.** Start in the existing repository and local Docker Compose setup. Store uploaded binary assets on a persistent volume with metadata and identity in PostgreSQL. Keep storage behind a common interface for future hosting when needed. Browser workflow tests, API tests, and non-destructive migration rehearsals are required for product increments. Model-assisted authoring arrives through an optional local or hosted provider adapter in W4. Manual authoring and validation use the same API.

The passes can ship separately and report W1 or W3 as partial until all of their checks pass. The first workspace pass uses the current records and makes catalog and time semantics visible. The image map pass adds storage and editing. W1 closes the shared typed property, relationship, evidence, time and access contracts before W2 builds general-purpose rules on them. W3 builds richer authoring and reading tools against those contracts, and W4 uses the manual workflows for proposals and imports.

Use multiple domains after defining each reusable contract. A ferry and relief inventory, a documented historical account, and a fictional encounter can test the same places, rules, actors and evidence. The fixtures establish only the behaviors they exercise.
