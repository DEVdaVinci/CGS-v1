# CGS Behavior and Acceptance Contracts

These contracts specify the first playable release, including the exact decisions needed at the write, read, planning and recovery boundaries. `openapi.json` defines wire shapes and `domain.schema.json` defines stored and proposed record shapes. `Persistence.md` defines durable ownership and relationships. Revisions are nonnegative integers. Ticks are fictional integer timestamps in the pinned world clock. Length is in integer centimeters. Timestamps for jobs are UTC instants.

## Session access and projection

| Operation | Current authority and returned view |
| --- | --- |
| Session and account | Accounts are provisioned by a Django administrator. The same-origin client reads a masked CSRF token from the session resource. Login and logout use Django CSRF-protected views. Login returns the authenticated session and fresh token. Failed login returns a generic invalid-credentials error. Protected routes normalize missing or expired authentication to `401 SIGN_IN_REQUIRED` at the API boundary. |
| World list and draft | Enabled world membership is required. Owners manage grants and inherit author rights. Editors need `edit_world` for manual writes, `delegate_draft` for proposals, `manage_guardrails` for policy edits and `publish_world` for explicit publication. Approval requires both edit and delegation. Any of these writing capabilities is subordinate to current membership and target scope. The draft is visible to the owner and enabled editors. |
| Published sources | Owners and editors can read the authorized editorial projection. A world reader with `read_source` can browse the published reader view, which includes explicitly public entries, facts and links. Player-only memberships see world title and run summaries and use the run projection for play. |
| Campaign access | An owner or editor with `manage_run` creates a run or assigns access. Play and read endpoints require an enabled world membership and an enabled run grant, including for the author when acting as a player. A `controller` can submit orders for the controlled actors validated against its grant. A `viewer` can read. A player order can be advanced, confirmed, cancelled or replaced by the account that submitted it. A manager can cancel a stuck order and retains no special power to execute its steps. |
| Model jobs | Bind the job to initiating principal, operation, source revisions, publication or draft and run scope, and the exact authorized audience when applicable. Fetches require that same principal and current access to the subject and all source pins. Queue, dispatch, finalize and read each check the effective policy. A user whose world/run membership or job authorization is revoked gets the same unavailable response as for a missing job. |
| World access changes | Owner updates a grant within the world lock. Disabling a world grant suspends every associated run grant until world access returns. Run membership and scope changes increment the world authorization epoch as well. Guards and source content have independent versions. |

The API returns the same `404 RESOURCE_UNAVAILABLE` body for an inaccessible or missing private resource. A reader who can already see the resource gets `403 ACTION_UNAVAILABLE` for a disallowed operation. Authenticated callers still receive field errors for malformed data after structural and scope checks without exposing hidden identities. A valid public-looking fact inside a private world is scoped to that world's real access grants.

### Selecting the audience and time

- `party` is the default audience. An actor audience uses `actor:<uuid>` and requires its own explicit read grant. Actor control and actor-private read permission are independent. The base fixture controller can order the scout to search and report through the party view. The scout's discoveries remain private to its actor view until an accepted report delivers them. The system can offer a generic report action and use an internal server choice of newly discovered facts. The ordinary player response can report completion without naming those facts.
- At request entry, capture the principal and current effective grants. Read grant inputs, pinned source, selected frame, event and order information in one short read-only Repeatable Read transaction. Set isolation before the first scoped query in the transaction. Authenticated session lookup can precede this when outside that transaction. The projection uses the committed authorization visible to that snapshot. A committed revocation before that boundary is effective. Evaluate actor control and world/run mutations under the serialized world lock. Project any returned receipt from a fresh authorized read after the write. Interleaving revocation can prevent delivery even when the earlier write was accepted.
- A historical view supplied by `revision` and/or `as_of_tick` selects the greatest frame within both bounds for that run. A requested nonexistent future revision returns `REVISION_UNAVAILABLE`. A tick earlier than the starting frame returns the same code. A future tick selects the latest accepted frame if there is one within the other bounds. The returned view includes the exact selected frame and bounds. The active order and pending actor status are included only on the latest unpinned view. A timeline cursor is scoped to source, run, audience, selected revision ceiling and the last delivered item. Use a signed, opaque cursor. Invalid or mismatched cursors return `INVALID_INPUT`. Order by stable IDs for wiki entries and accepted revision ascending for event lists. Default page size is 25 and maximum is 100.
- Returning an order requires the submitting account or an authorized run manager and current access to its exact audience. The run view omits an order outside the selected audience. Detailed plans and step pins require the submitting account and current control of the actors in the plan. When only order status is authorized, return empty `steps` and null plan, next-step, job, issue and receipt fields. The manager may cancel a stuck order within this scope. A direct receipt read enforces the submitting principal and current receipt scope.
- A direct event, accepted receipt or narration projects facts at that event's **resulting frame** for the permitted audience. A blocked receipt projects its reason at its before frame. Each log row uses its own saved event frame even when it appears inside a later frame's view. The result can show a generic action summary when the names or location are withheld. An event with no permitted disclosure at that frame is unavailable. A historical party read of the search still omits the hidden passage after a later report. Only a later frame or later event can disclose that fact through ordinary play. Editorial source views have their own authorization pathway.
- A fact is visible at a selected frame when its source version matches, its validity interval covers the tick and the audience knows it through public scope, initial observation or an accepted observation at or before that frame. Check permissions on the fact's subject, any ID in its value and any claimant. Include only readable source-reference IDs in the projected fact and only readable endpoints in projected links. An attributed claim retains its full claimant, cited sources and effective interval in the source. Multiple characters can disagree. A publish-required verified fact with the same subject and predicate has at most one effective value at any tick. Authored intervals are half-open. An observation stays as history after a fact's interval ends. It can support a historical or explicitly attributed event read at that older tick. Gaps stay unknown. Never make a private record discoverable through name matching or error text.
- Retrieving model context starts with the authorized projection and purpose, then exact ID links and a bounded text filter. The provider receives a purpose-specific DTO, never the stored snapshot. Drafting reads the current private world slices explicitly delegated by the author and an immutable, built-in reference catalog version. Apply this first-release source boundary to request, dispatch, result display and approval. World membership/guardrail changes make stale pinned jobs or proposals superseded. A call already dispatched under the captured grant may return. Its output is withheld when the current checks fail. Collect diagnostics by outcome code, without raw input, secrets or hidden rule failures.

## Authoring rules

Manual and assisted writes share `apply_draft_edits`. Create starts at draft revision 0 with an empty document and an active policy version 1. The default policy delegates zero operations and names zero locked or reserved fields. An owner or authorized editor chooses a scope before requesting AI work. The draft can hold incomplete records. A missing required draft field is omitted and appears as a typed problem with a JSON pointer. An explicit null is allowed only in a schema field that declares it. Publication reports any missing required data, invalid references and route or rule failures before sealing the document. A reserved optional lore field can remain absent.

Each `DraftProposal` is **one immutable, atomic review group**. The proposal holds its ID, base revision, world epoch, guardrail version, allowed source pins, edits, assumptions and questions. The digest covers identity, all of those pins and the ordered edit list. Canonicalize validated text as UTF-8 NFC, object keys in lexicographic order, integer values in decimal, arrays in submitted order, and compact JSON. Digest encoding is lowercase SHA-256 hex. The client displays the complete group and submits its ID and digest via explicit approval. To separate linked changes the author requests a fresh proposal for the smaller scope. One failed check rejects the whole group. The validator verifies allowed source references, current policy, writer rights, each touched path, lock/reservation rules, references and final typed shape.

Accept `add`, `set`, and `remove` edits at restricted JSON pointers below `entities`, `facts`, `links`, `layout`, `rules`, and `start`. A pointer names a record or a registered field. `add` requires an absent value. `set` requires a present value of the matching domain type. `remove` deletes an eligible field or record. Replace array fields as a unit. Whole-record writes are checked against every changed leaf. Reject unknown pointers and writes to immutable IDs, kind, frame identity, version metadata or a previously issued identity's meaning. `@name` aliases within a reviewed group are permitted only in a new ID path or a typed identity/reference slot. Resolve them consistently across the entire candidate change, reserve entity keys in the same transaction, and save the mapping in the receipt. Any reference to an undefined alias rejects the candidate. A missing optional field that the AI is forbidden to fill remains absent. An editor can answer it manually unless a separate all-writes lock protects it.

Run under the world lock. Check current write permission before receipt lookup. A matching authorized request returns the original receipt with the original response code projected under current access. A different payload attached to the same key returns `KEY_REUSED`. Only a fresh request checks expected revision, current policy, group digest and engine validation. Commit the new immutable revision, new head and receipt together. A publication request selects the exact current draft revision, requires a separate permission and explicit action, and seals a validated immutable source with its own receipt. A later correction forks a new approved publication from the current draft with a parent source reference. An existing run retains its approved source.

## Order identity and state transitions

Store the exact submitted text or typed steps, ordering constraints and original budget. A published plan has `plan_revision` and a stable `step_id` per step. Plan revisions start at one after planning. Replanning publishes a new immutable plan and new IDs for unaccepted steps. Prior accepted steps remain only in their original plan/history. The active order holds the current plan pointer and next index into that plan. A player must send that plan revision and step ID with the expected run revision. An active slot continuing at the same run head still changes plan identity when its pending work changes. Advance is legal only in `ready` with all pins current and that step at the cursor.

| Order state and operation | Next state and durable effect |
| --- | --- |
| New typed order with a fresh head | `ready` with a checked plan. Each typed step is exact and is rechecked against authoritative state on advance. An unavailable or ambiguous reference produces a typed error and creates no order. |
| New exact text or bounded goal | `planning` and one job, committed together. For exact text a complete supported parse can publish directly as `ready`. Match every clause, actor, target, quantity, ordered sequence and explicit restriction. Confirmation is required for an otherwise valid model interpretation when the parser cannot prove equivalence. |
| Planner publishes | `ready` for a valid exact parse or a delegated plan within all original boundaries. Publish `awaiting_confirmation` with an immutable draft plan for other valid interpretations of exact text. Ambiguous or materially incomplete plans become terminal `needs_input`; show the question and allow a new order. A malformed or out-of-policy output becomes terminal `failed`. |
| Confirm exact-text interpretation | From `awaiting_confirmation` only, require expected run head and the same plan revision, then record explicit approval and enter `ready`. Cancellation or replacement is available. An older plan cannot be accepted by confirming a different plan at the same head. |
| Replan a delegated remainder | An initiating player can request a replan of a `ready` delegated order at its current run and plan revisions. Require a pending player step, remaining step and planning budgets, and no owed NPC response. Store idempotent job intake, increment the planning count and enter `planning` together. Return `202` with the job and order IDs. Reject other states with `ORDER_STATE`. An exhausted order can be replaced or cancelled. The saved intent, accepted history and remaining limits govern the new plan. The current game head is unchanged. |
| Valid ready advance | Commit one step, receipt and event with the updated frame. Increment accepted count and plan cursor. Finish at `completed` when the plan ends or a stop predicate is reached. The saved step identifies its original plan. Stop predicates are checked on committed state. |
| Block, stale request or actor duty | A valid fresh step that fails its world rule moves the order to `blocked`, returns a scoped result and takes no tick. A stale request returns a conflict with no accepted event. A stale request for an old plan does not pause a newer ready plan. While a system actor step is due, return retryable `ACTOR_TURN_DUE`. This temporary response creates no step receipt and allows the same key to be retried. |
| Head changed outside this order | On NPC resolution or a conflicting external change, a pending typed/exact remainder must be reconfirmed at the new head using a new immutable plan. The pending delegated remainder enters `planning` with a new plan job if budget allows, or `needs_input` if planning is exhausted. A blocked order remains blocked until the player replaces or cancels it. |
| Job failure or supersession | If the job still owns a planning order, exhausted retries, lease expiry at its last attempt, cancellation of the job, invalid output or provider refusal release the slot with an explicit terminal status. Use `failed` for execution failure, `needs_input` for clarification or stale context requiring choice, and `cancelled` for an explicit order cancellation. Finalizers for replaced/cancelled orders leave the new order alone. A new typed order is allowed in each case. |
| Replace or cancel | The terminal state of the earlier order is `replaced` or `cancelled`. Close that order and supersede its job in the same write as a replacement when requested. Prior accepted steps and receipts remain readable. A new order starts with its own limits. |
| Resume | The unpinned view returns current head and a readable active order with plan pin, next step and state, plus the last readable disposition for that order. An existing receipt can be read by request key within the caller's order scope. Client retains the opaque command ID, idempotency key and requested plan/step pins through refresh. Clear them on logout or completed recovery. The server models the pending work. |

Run one active player order across `planning`, `awaiting_confirmation`, `ready` and `blocked`. Terminal statuses are `completed`, `needs_input`, `failed`, `cancelled`, and `replaced`. An order with `max_steps` counts accepted player steps across all its plan revisions. A blocked step uses no accepted-step budget and does not roll. Bound a delegated order to three model planning jobs including replans. Use at most two provider calls per job. An unrecoverable ambiguity closes the order with a visible question. `max_focus` limits actual cumulative accepted spend. A `stop` of `after_report` stops at the first accepted report by an allowed actor. `complete_plan` permits the allowed plan to finish. Typed operations and exact raw text also use an eight-step maximum for this release. Provider text cannot increase limits or alter exact approved clauses.

Store each accepted or blocked step and stale plan/head attempt for a currently authorized caller under the scoped key and normalized payload digest. Persist a stale receipt with its original response code and permitted conflict refs. Other preparatory failures such as malformed input, denied auth, job still planning, due actor step and invalid cursor are ordinary responses without a new receipt. A same-key request after a durable result is exact replay or `KEY_REUSED`. A new logical step gets a new key. Receive attempts under the world lock and check the scoped receipt first. For a fresh request, compare the head, then the published plan and its next step, then readiness and any owed actor step. A mismatched head returns `STALE_RUN`. A superseded plan or changed next step returns `STALE_PLAN`. An order without a published plan or an executable cursor returns `ORDER_STATE`. Resolve rule, roll, event, updated frame, order cursor, any deterministic trigger and receipt in one transaction. Avoid saving private reason values in public response fields. Keep actual source IDs and typed internal violations for authorized evidence.

### Deterministic scheduling

A committed player event can set one pending response trigger with its causal event ID. A dedicated rules loop claims pending runs through the same world lock and resolves the supported policy under its actor knowledge. Store one unique system result per triggering event and responding actor. An accepted system action advances the head as its own event. A hold or blocked system candidate records its audited outcome, clears the pointer and takes zero ticks. The worker and a player's next step compete through the world lock. An owed response is eligible even while the separate inference process waits. This uses one codebase, one database, and distinct API, rules and inference process roles.

## Inference jobs

| Transition | Durable behavior |
| --- | --- |
| Enqueue | Persist kind, principal/scope, input subject and pins, job ID, attempts 0, max attempts 2, budget deadline and next eligible time. An idempotent retry gets the same job. |
| Claim due job | Lock only the job row during claim. Set `running`, increment attempts, assign a fresh lease token and a 40-second lease, then release the claim transaction. Confirm current scope and pins in the world scope before dispatch. Network inference runs outside the lock. Timeout per provider call is 25 seconds. One claimant per row and token. |
| Retry transport failure | Current owner token can return a transient timeout or service failure to `queued` with a two-second delay if an attempt remains and the deadline allows it. Reclaiming an expired lease increments the attempt count and changes the token. Use a total 70-second job deadline from initial enqueue for user-facing failure. |
| Complete | In a short world transaction, lock in order world → subject → job, check live token, expiry, scope, source pins and subject state. Attach a validated proposal, plan or readout and advance linked order in the same transaction. Stale/cancelled subjects make the job `superseded`. A changed source or current scope requires a fresh authorized request. |
| Expire or fail | After checking due actor work, the rules loop scans a bounded batch of deadlines and final expired leases and rechecks each in world/subject/job order. If still active, retire the job and release the order slot with `failed` or `needs_input`. A late token cannot attach a second result. Release an order only if linked to this job and still planning. |
| User recovery | `GET /jobs/{job_id}` returns enabled status, sanitized reason, optional result reference and retry guidance. Transient automatic retries use the same job. After terminal failure a new generation request creates a new job. A planning failure allows typed input or a new text order. A readout retry starts a new job and leaves the committed event intact. |

Use a durable, idempotent generation request for each model-dependent task. The structured result is validated independently of provider JSON schema success. Pause exact command execution for explicit confirmation when its meaning could differ from the stored plan. Show enough named actions, targets and order for the player to confirm. A bounded choice may vary under the delegated limits and allowed knowledge. Optional generated narration selects from permitted presentation templates with safe references. The service renders all game facts from the saved scoped outcome, with a deterministic rendering as soon as the step commits. This prevents extra unverified claims in readouts and keeps a retry of presentation separate from a retry of gameplay.

## Rule resolution and exact fixture

Validate the actor's active state, authority, granted rule identity, rule version and permitted target under the locked run head. Supply a specific rule UUID in every typed action, including Move and the Ward Step variant. Verify that the rule template matches the action and that the rule is in the actor's authored or earned grants. Validate one draft source for legal geometry and references before publication. The rule engine uses the pinned version of the handler. A software upgrade retains the handler needed by active published versions or requires an explicit migration of the application support boundary.

| Action | Preconditions and accepted effects |
| --- | --- |
| SEARCH | The scout must be in the rule's named place. Its `discovery_fact_ids` identify effective discoveries. Add one observation per new actor/fact pair. If the scout already knows all candidates, return `NO_NEW_OBSERVATIONS` with no tick. The event is visible as a generic search to party scope. The precise observations and geometry wait for disclosure. |
| REPORT | Use a permitted audience named on the report rule. The reporter can share only facts it knows at that frame and can disclose, excluding author-only facts. The generic `new_discoveries` means effective facts learned by this actor during the run and unavailable to the target audience. Specific fact IDs require the same checks. Reject with no tick when no new authorized facts can be delivered. An accepted report adds first knowledge records at the new frame. The discovered fixture fact's typed reference list reveals the listed areas, points and edges. A separate sighting reveals the sentry identity and its permitted current location if that point is known. |
| MOVE | Use the current point and the known traversable graph. Treat each authored edge as undirected for this release. Edge length is the ceiling of Euclidean distance in cm. Validate endpoints inside authored rooms and walkable segment coverage in the canonical layout. Prohibit ending on another occupied point and exclude occupied intermediate points from the route. A known occupied endpoint gives `OCCUPIED`. A reachable route beyond the supplied rule's budget gives `MOVE_LIMIT`. A target or cause outside the audience's scope gets a generic reason. Choose the shortest permitted route and use ordered point UUIDs to break ties. Charge the pinned focus cost only when movement is accepted. |
| CAST | Require the granted cast rule, living target with the configured role, enough Focus, squared range within the rule's squared cm budget and a straight line of effect within the reachable authored room/corridor union. Endpoints and segments are checked against the immutable coordinates and permitted connection rules. Draw only after legality, one integer 1–20. Spend the cost on every accepted hit or miss. Floor damage at zero HP, mark defeated at zero, and make the defeated state non-occupying while preserving the point. An accepted attempt can make a pinned stimulus fact known to the living target through this event. An alert profile that observes it can request one engine-owned move. A hold profile requests no response. |
| PROGRESS | Evaluate once for the encounter-clear transition to zero sentry HP. Use `rewarded_encounter_ids` in the frame to prevent a second award. Award the configured XP, qualifying level, unspent points and Ward Step together with the accepted hit. Rank comes from the separate authored actor record and this progress rule leaves it at C. Ward Step is an ordinary granted MOVE variant of up to 300 cm costing one Focus. |
| ALLOCATE | Sum the listed positive changes, using zero for omitted attributes. Require total > 0, each result within the attribute bound, and total within unspent points. Apply attribute and spending effects together. An invalid allocation leaves the head unchanged. |
| WAIT | Use an authorized scheduled actor or explicitly typed authorized request. Advance one tick when accepted. Holding without a scheduled action takes no tick. |

Public points and actors are shown only when their required visible place and projected references are available. A located opponent's current token is shown when its identity and current point are known. Controller-scoped character sheets show resources, progression and usable rules. Other actors expose only permitted fields. For an illegal action use a generic safe code where a specific failure would reveal deliberately concealed state. The client renders the map from the approved room bounds and coordinates, and tokens and sheet from the selected frame.

The fixture's reference west junction is public. The corridor and chamber are observed regions. The sentry is defeated after the reference two hits. The alternate branch costs one additional Focus for a miss and can use Ward Step after the third accepted cast. The corrected source adds `midpoint` at (0,350) cm between the junction and threshold at (0,700) cm. Its two 350 cm edges make the scenario playable even though a single 700 cm move exceeds the six-meter budget. All previously observed positions in a v1 run remain tied to that run's immutable source.

The alert and obstructed-alert cases use separate source instances derived from v1. A scripted miss at head 3 makes the stimulus known at head 4 without defeating the sentry. The alarm candidate uses the sentry's knowledge of the route to the alarm point. With the route open it accepts its own step at head 5. With that edge closed it records a blocked system attempt and leaves head 4. Process it independently of any slow inference request. Keep known geometry, evidence scope and recorded event attribution separate from the actor's choice.
